# Delivery, supply-chain, agent-quality and MCP evidence on the repository-health spine

The change hangs a large set of new evidence sources off the existing repository-health grade and pull-request gate. Supply-chain documents (CycloneDX, SPDX, VEX, SLSA provenance), diff coverage, mutation, axe and eval reports all come in through the one health upload door. GitHub delivery data comes from a leased syncer, a CI push door and an HMAC-verified webhook. OTLP GenAI traces have their own receiver. Each new source becomes an opt-in grade metric and an opt-in gate input. On top of that sit read-only scorecards, a portfolio heatmap, a read-only MCP server with a stdio proxy, Jira/GitHub issue creation through the vault, AI test proposals, a boot-time vault key rotation and an hourly session sweep. Authorization holds up well: every new route has a guard, the webhook is the only new `open` row, uploader pins carry through, and every new query I read is constrained by `workspace_id` on both sides of its joins. The defects are in what the gates and verifications claim, not in who may call them.

Watch for: the eval, runtime and delivery gate inputs turn "insufficient", "no baseline" and "no run" into a pass (**confirmed**). SLSA L2/L3 is reachable without binding the provenance to the artifact, and without checking who signed under a configured CA root (**confirmed**). MCP server URLs that contain credentials are stored verbatim and returned to viewers (**confirmed**). A failed audit write in a background eval run is an unhandled rejection that can take the API down (**confirmed**). The delivery syncer's lease has no renewal or ownership check, so a slow sync can run twice and move cursors backwards (**likely**). The issue-link stale-claim takeover can delete a fresh claim and open two issues (**confirmed**).

**Verdict**: NEEDS_CHANGES

## High-level view

The gate gained four opt-in inputs: diff coverage, delivery (DORA), AI governance, and agent quality (evals + runtime). Diff coverage and the AI-governance coverage rule fail when nothing was measured. Delivery, evals and runtime only fail on an explicit `fail`. An eval suite with no baseline, or a branch with no eval run at all, adds nothing to the gate, so `gateOnEvals: true` passes a PR that never ran its evals. That breaks the repository's "not configured / insufficient is never a pass" rule, and it is inconsistent with how the change itself treats diff coverage.

`rateDifference` matches Newcombe's method 10 over Wilson intervals, and a credible regression fails even on a thin sample. The one statistical weakness is that repeats of the same case are pooled as independent trials in the overall rate, which overstates significance (**likely**, nit).

Provenance verification gets DSSE PAE, chain walking and digest selection right, but the policy layer is too permissive. Without `expectedDigestSource: 'upload-query'` there is no expected digest, `subjectMatches` is `null`, and a correctly signed provenance for any other artifact still reaches L2 or L3. With a CA root configured (Sigstore/Fulcio being the obvious one), the leaf certificate's identity (SAN, OIDC issuer) is never checked. Anyone who can get a Fulcio certificate can produce "verified" provenance.

Delivery uses a `FOR UPDATE SKIP LOCKED` lease claim in the report-dispatcher style, writes per-stream cursors, and handles rate limits honestly. But the lease never renews and `finish`/`updateSource` don't check that the caller still holds it. A sync that outlives ten minutes is re-claimed and runs concurrently, and the later writer of the whole `cursors` JSON wins. Separately, the listing reads are newest-first and page-capped while processing goes oldest-first from the capped set. A backfill with more than about 500 updated PRs, or 300 commits or runs, permanently skips the oldest ones.

The webhook is shaped well: opt-in twice, a per-client budget, a 1 MB limit, the HMAC checked over raw bytes before parsing, and a replay store. The replay store is keyed on `X-GitHub-Delivery`, which GitHub does not sign, so a captured body re-sent with a fresh id gets through. Impact is bounded: it only queues a sync, and queued syncs are absorbed.

The MCP server is a thin read-only layer over the same health options the routes use, guarded `viewer`, stateless, with contract-parsed answers. The stdio proxy and the CLI both refuse plain http to anything but loopback, and the CLI refuses redirects. The composite action's shell version of that check accepts `http://127.anything`, and the CLI keeps its own second definition of "loopback".

The agent-config scanner keeps env-variable names only, but stores and returns each MCP server's `url` verbatim, including any query-string credentials it has just flagged. The local walk also reads untracked files like `.claude/settings.local.json`.

Resource bounds are mostly explicit: body limits, gunzip `maxOutputLength`, span caps, retention pruning. Two text normalisers can go quadratic. Failure clustering runs on unbounded test messages and re-tests a prefix slice per quote match. The secret redactor's private-key pattern rescans to the end of the input for every unmatched `BEGIN`. The eval runner's regex guard plus the vm timeout bounds each match, but each timed-out check blocks the event loop for 250 ms.

Issue creation goes through the vault with a claim row. The stale-claim takeover is not a compare-and-swap. A tracker's base URL can also be repointed while its stored token is kept, which sends that token to the new host.

## Gate wiring: what an opted-in input does when nothing was measured

`evaluateHealthGate` grew four optional inputs, and they disagree about absence. Diff coverage under `minDiffCoverage` fails when unmeasured ("a number nobody measured is not above a minimum"), and so does the AI-governance coverage rule. Delivery, runtime and evals contribute a reason only on an explicit `fail`:

```ts
// packages/projects/src/health/gate.ts:85, 110, 113
...(delivery?.status === 'fail' ? delivery.reasons.map(...) : []),
.filter((suite) => suite.verdict === 'fail')
agents.runtime?.status === 'fail' ? ... : []
```

The eval path has a second hole upstream. `evalGateReading` drops every suite whose comparison is `null`, which means no baseline on the default branch (`eval-service.ts:438`). `agentsGate` then returns `null` when the list is empty. So with `gateOnEvals: true`:

```
branch has no eval run        → suites []          → gate passed
suite has no baseline         → dropped             → gate passed
fewer than minEvalAttempts    → verdict insufficient → gate passed
suite exists on main, deleted on branch → never compared → gate passed
```

The comment in `eval-regression.ts` says "insufficiency withholds a pass". The scorecard does withhold it, but the gate converts the withheld pass back into `passed`. The delivery comment states the trade-off on purpose ("an absent number is above no maximum"). It still contradicts the repository rule this review was asked to hold, and it contradicts the diff-coverage choice made in the same function. The suite also gates on the branch's latest run of each suite whatever commit it ran on, so an eval from an earlier commit can stand in for the gated one (**likely**).

The AI-governance path is consistent with its own documented default: an unsynced PR is `unknown`, which is treated as `human`, and `human` is `not-applicable`. `unknownReason` makes the default visible, and `treatUnknownAs: 'agent-authored'` is the strict switch. Governance only runs on the `POST …/health/gate-report` path. `GET …/health/gate` and the MCP `get_gate` tool never evaluate it, so the two can disagree on the same branch (**confirmed**, informational).

## SLSA provenance: verified, but of what, and by whom

Two policy gaps undo the level `provenance.ts` reports, though its signature and chain checks themselves are sound.

The first is subject binding. `subjectStatus` returns `null` when `expectedDigests` is undefined, and `provenanceTrust` only sets it when the upload carried `digest=`. Only `expectedDigestSource: 'upload-query'` makes the digest mandatory, and that field is optional in `SupplyChainProvenancePolicySchema`. The level then only requires `subjectMatches !== false`:

```ts
if (isSlsa && subjectMatches !== false) {
  slsaLevel = 1;
  if (signature === 'verified') slsaLevel = builderAllowed === true ? 3 : 2;
}
```

Any validly signed provenance, for any artifact, any project, any earlier build, earns L2/L3 for whichever project it is uploaded to.

The second is signer identity under a root. `chainVerifies` proves the leaf was issued by a configured CA. For Sigstore's public-good Fulcio root, the configuration this feature is obviously built for, that proves only that someone with a GitHub (or any supported OIDC) account requested a certificate. The leaf's SAN and the OIDC issuer/workflow extensions are never read. Combined with a builder allow-list containing `slsa-github-generator`, a provenance produced from an attacker's own repository is L3 here. The `at = now` validity check means the certificate must be fresh, and a CI job uploading within ten minutes of signing is exactly the normal flow (**confirmed** by reading. I did not construct the forged bundle).

Rekor not being checked is stated in every summary. That is a different, honestly disclosed gap.

## Delivery syncer: one lease, several writers

```
worker ──▶ delivery_syncs(queued) ◀── operator / webhook (queueDeliverySync)
                    │ claim: UPDATE … WHERE id IN (SELECT … FOR UPDATE OF d SKIP LOCKED)
                    ▼            status=running, next_attempt_at = now + 10 min
            API syncer.runOnce ──▶ GitHub (token from vault) ──▶ pull_requests / commits / deployments
                    │                                     └──▶ delivery_sources.cursors (whole JSON)
                    ▼
            finish(): UPDATE delivery_syncs WHERE id = row.id   ← no lease/owner predicate
```

The claim re-takes a `running` row once `next_attempt_at` passes, which is the crash-recovery path. Nothing extends the lease while a sync runs. One sync is 30 PRs × 3 list calls × up to 3 pages, each page with a 15 s timeout and two retries, plus three more streams. It can outlive ten minutes on a slow or secondarily rate-limited GitHub. A second process then claims the same row and both run. Because `finish` and `updateSource` match on `id` only, the slower one's writes land last. `updateSource(row, { cursors })` replaces the whole cursor object from that process's in-memory copy, so a stream can move backwards. The upserts make the re-read harmless, but the module's headline guarantee ("cursors move only forward") does not hold under concurrency (**likely**).

The `NOT EXISTS` guard against two live syncs of one source is evaluated against the statement's snapshot. Two queued rows for one source can therefore be claimed by one statement, or by two processes racing on different rows (**likely**). The worker's enqueue doesn't consult `queueDeliverySync`'s "already queued" check, and `queueDeliverySync` is itself check-then-insert, so duplicate queued rows are easy to produce. A sync that deterministically kills the process is reclaimed forever: `attempts` is incremented by the claim but compared to `maxAttempts` only in `failed()` (**likely**, nit).

## Delivery backfill window

`listPullRequests` reads newest-first (`sort=updated&direction=desc`) for at most 5 pages and stops at `newerThan`. The syncer then sorts that set oldest-first, processes 30, and advances the cursor to the last processed `updated_at`. If more than 500 PRs were updated since the cursor (the first sync reads 90 days), the 500 read are the newest. The cursor eventually walks to the newest one, and everything between the old cursor and the oldest of those 500 is never read. `syncCommits` (3 pages, newest-first, cursor to max `committedAt`) and `syncWorkflowRuns` (3 pages, cursor to every listed run's `created_at`) have the same shape at 300 items. Deployments are read with a 24 h lookback and the cursor advances past a deployment whose status is still pending, so one pending longer than a day is lost (**confirmed** by reading). Separately, `since=` on commits filters by commit date, which predates the push for rebased or merged branches. That is a known GitHub-API caveat worth one sentence in the guide.

## GitHub webhook receiver

The weak point is replay. GitHub's `X-Hub-Signature-256` covers the body only. `X-GitHub-Delivery` is an unsigned header, so the replay store keyed on it stops GitHub's own "Redeliver" but not an attacker who captured one signed body and sends it again with a new id (**confirmed**). The blast radius is small because a payload only names a repository and at most queues one absorbed sync, but the module's "a captured request re-sent later … is refused" is not what happens. Keying on sha256(body) fixes it, and GitHub's redeliveries are byte-identical.

Two smaller observations. The delivery id is recorded before the event is handled, so a DB failure in `handleGitHubEvent` makes GitHub's own retry a `409 WEBHOOK_REPLAYED`, and the event is lost (**confirmed**). In LAN mode the global client allowlist runs before this route, so GitHub's hook addresses are refused unless an operator adds them to `ALLOWED_CLIENT_CIDRS`. The guide should say so (**likely**). The prune (`DELETE … NOT IN (SELECT … LIMIT 10000)`) also runs on every delivery.

## Credentials that leave the vault's custody

The agent-config inventory stores each MCP server's `url` verbatim (`agent-config-service.ts:210`, from `serverEntry` in `agent-config-scan.ts`). `GET …/agents/mcp-servers` returns it to every viewer. The same scan raises `agent-config/mcp-secret-in-args` for exactly the credentials that URL carries (`?api_key=…`, userinfo, token shapes), so the product detects the secret and then publishes it. The local-checkout walk (`collectAgentConfigFiles`) reads untracked files, and `.claude/settings.local.json` and `claude_desktop_config.json` are conventionally local and secret-bearing, so this is not limited to what the repository already committed (**confirmed**).

`setIssueTracker` lets an admin change `baseUrl` without re-supplying the token. The next issue creation sends the stored Jira bearer token to the new host. Admins are already trusted, but the point of the vault is that holding the admin role does not mean holding the credential. Repointing a credential at a new origin without re-entering it turns an admin session (or a CSRF on it) into token exfiltration (**confirmed**). `HttpsBaseUrl` refuses http and userinfo but allows internal https hosts, which makes this a server-side request primitive for admins too (**likely**).

## Background eval runs and the process

`createAgentQualityRoutes` schedules with `(task) => void task()`. Inside the task, `record('evals.dataset.run.failed', …)` in the catch and `record('evals.dataset.run.complete', …)` after it are bare awaits on `audit`, which writes to the database. The API installs no `unhandledRejection` handler, so a database blip during a background eval rejects the floating promise, and Node's default terminates the process (**confirmed**). `onRunFailure` exists, and the fix is to route the task's own rejection to it.

The "already running" guard checks `running.has` in `prepareDatasetRun` and only `add`s inside `execute`, with the start audit awaited in between, so two near-simultaneous POSTs both run, spending the model budget twice. The set is also per process.

The regex check's vm-context timeout is a backstop, not an isolation: each timed-out match still holds the event loop for the full 250 ms. A dataset of polynomial-but-allowed patterns (`\d*\d*\d*…x`) across 1000 attempts degrades the whole API in 250 ms slices. Operator-only, so a nit.

## Text normalisers on input nobody bounded

`failureSignature` normalises the full failure message before slicing to 400 characters. The quote step calls `MEANINGFUL_QUOTE.test(text.slice(0, offset))` for every quoted span, which is linear in the prefix per match and so quadratic in a message made of `'' '' '' …`. Failure messages come from uploaded run results, and clustering runs on every insights and test-effectiveness read, so one uploaded report can pin a CPU per dashboard load (**likely**; I did not find an upstream cap on `test.error.message`).

`redactSecrets`' private-key pattern `-----BEGIN … PRIVATE KEY-----[\s\S]*?-----END …` restarts a scan to the end of input at every unmatched BEGIN. It runs before the 8 KB cap, on content from an OTLP export of up to 8 MiB, when `storeTraceContent` is on (**likely**). Both fixes are one line: bound the input, or bound the lazy span.

## Transport checks: three implementations of "loopback"

The stdio proxy uses `isLoopbackBind` from `@automate/config`. The CLI has its own `isLoopbackHost`. The composite action has a bash `case`. The CLI copy differs from the config one: it does not accept an IPv4-mapped `::ffff:127.0.0.1`. The bash copy is wrong. `127.*` is a glob over the hostname, so `http://127.attacker.example/` passes the "Check the destination" step and the uploader token goes out in cleartext. The CLI's `redirect: 'error'` and same-origin assertion are good touches that the curl steps match by not passing `-L`.

## Concurrency in line maps and issue claims

`storeLineMap` reads the commit's line map, merges the new shard in memory and upserts the result. Two shards of one matrix job uploading at once each merge into the same old map, and the last write drops the other shard's lines, so diff coverage for that commit reads low until something re-uploads (**likely**).

The issue-link stale-claim takeover is not a compare-and-swap. Both takers read the stale `prior`. A deletes it and inserts its own fresh claim. B's `delete … where state = 'pending'` then deletes A's fresh claim, B inserts, and both call `createIssue` (**confirmed**). An adapter that throws rather than returning an error result also skips `release()`, which blocks the source for `STALE_CLAIM_MS`. Releasing the claim after an ambiguous 5xx is documented as deliberate and is left as is.

## Vault rotation scope

`rotateVaultSecrets` re-seals the entries of `runtimeConfig.workspaceId` only. If two workspaces' installs share one database and one `VAULT_SECRET` (the syncer and worker already operate across workspaces), the other workspace's entries stay under the previous secret and become unreadable once `VAULT_SECRET_PREVIOUS` is removed (**possible**: depends on whether a shared-database, shared-secret deployment is supported. `docs/quality/tenancy-scope.json` and the deployment guide would say). During a rolling restart, instances still on the old secret cannot open rotated entries. That deserves a sentence in the operator guide.

## Test coverage

Isolation coverage follows the `AGENTS.md` shape: there is a per-service isolation case, a tenancy row per table, and a family entry in `workspace-isolation.test.ts`.

Not tested: concurrent syncer runs past the lease, or two processes claiming one source; a backfill larger than the page caps; a webhook body replayed under a new delivery id; two concurrent stale-claim takeovers; concurrent shard uploads of one commit's line map; a background eval whose audit write fails; a provenance with no expected digest reaching L≥2 (the property suites appear to assert the level formula rather than refute it); a Fulcio-rooted leaf with an unexpected identity; `127.x.example` against the action's destination check; a URL-embedded credential in the MCP inventory response; quadratic inputs to `failureSignature` and `redactSecrets`. I did not run the build or the test suites for this review.
