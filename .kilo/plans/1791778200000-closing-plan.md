# The closing plan — Automate, from evidence console to working tool

The last plan this repository writes. Everything before it landed; this one closes
the loop, makes the claims mechanically checkable, and names honestly what cannot
be closed from a development host.

Date: 2026-10-12. Baseline: the tree after L0 (decision records) and L1 (the
coverage join), every gate green.

---

## 0. What is actually left — measured, not remembered

| Layer | State |
|---|---|
| Measurement | **Done.** Score with source and citation, findings engine in `lib/findings.ts`, 50-tool catalogue, toolchain probe, per-file coverage join, 17 project routes |
| Decision | **Done.** migration 0026 + `decision_records`, `DecisionStore` with one shared validation rule, Drizzle and in-memory implementations, 26 parity scenarios against both, POST and GET `/projects/:id/decisions` |
| Screens | **Partial.** `tools` and `insights` land with evidence and citations; the five deep-dive screens exist but have no project switcher; `analytics` is quarantined to the KPI grid |
| The loop | **Not connected.** No screen reads a decision back. The table has rows; no human sees them |
| Memory | **None.** `ScoreTrend.points` is 2 because the history table was refused as a second authority |
| Action | **None.** The five agent domains answer `501`; `qa/gaps` computes `cheapestClosure` and nothing acts on it |
| Ledger | 10 open, 7 debt. Four closable with code, four blocked on hardware, three blocked upstream |

**The single sentence this plan exists to close:** the product measures quality
and records decisions, but a QA/SDET still cannot open it in the morning and be
told what to do.

## F0 — Close the loop

*Nothing else in this plan matters if this does not land. It is also the smallest
diff in the plan and the only one a tester feels the next day.*

### F0.1 — The inbox query

`GET /api/v1/projects/:id/decisions` gains two predicates on the indexed columns
that already exist (`decision_records_workspace_owner_idx`):

- `?verdict=open&ownerId=<me>` — what is waiting on me, oldest first
- `?decidedBy=<me>&since=<7d>` — what I decided

**Gate:** one test per predicate, asserting the SQL order matches the in-memory
order (the parity shape `store-parity.test.ts` already establishes).

### F0.2 — `/dashboard/today`

One screen, four blocks, no new design language — the glass chrome and
`StatCard` the design system already ships:

| Block | Source | Already built |
|---|---|---|
| What changed | `GET /…/qa/score/diff` | yes, live, no screen reads it |
| What broke | `deriveFindings` + pending decisions | yes |
| What's waiting on me | F0.1 | one predicate away |
| What I decided | 7-day timeline of `decision_records` | the table exists |

**A week with no verdicts is a week the loop stopped, and the screen says so**
rather than curating it away.

**Gate:** enters `route-state-matrix.test.ts` the day it is written — that gate
fails a route added without a row, and each row must name four state test-ids its
own source renders. Plus the axe sweep, plus the composition rules (one h1,
`max-w-measure`, `numeric` on figures).

### F0.3 — Trend, derived and marked derived

One table, `derived_score_points(project_id, at, total, labels)`, written by the
score service on each read. **Not a second authority for the score**: a derived
point is a photograph, never a re-derivation, and the row and the doc comment both
say so. That is how `ScoreTrend.points` becomes 30 instead of 2 without a fourth
blocking number.

**Gate:** a test that two consecutive reads of an unchanged window produce
identical points, and a test that a changed cell moves the newest point only.

### F0.4 — The decision timeline

`GET /api/v1/projects/:id/decisions/timeline` — verdicts by week, by owner, and
the count of findings with no verdict. Rendered on the today screen.

**Gate:** the same parity shape as F0.1.

### What F0 does not close

Nothing in the ledger. It is the wave that makes the ledger worth closing — a
product nobody opens cannot be measured into quality.

## F1 — Make it trustworthy

Each of these four takes a claim this repository makes about itself and makes it
mechanically checkable. **This tier is why a QA/SDET should believe the numbers.**

### F1.1 — C-4: split the execution store

`drizzle-execution-store.ts` is 2,166 lines and holds six of the 34 complexity
offenders (73, 71, 67, 42, 19, 19 against a ceiling of 15);
`in-memory-execution-store.ts` holds two more.

Split along seams the files already contain — outbox, canonical projection,
artifact lifecycle, lease reaping — into four modules per implementation, with the
parity suite as the proof the split did not change behaviour.

**Gate:** `store-parity.test.ts` (26 decision scenarios + the execution ones)
stays green through every move, and the complexity ceiling is unchanged rather
than raised.

**Why this is first in F1:** the store is where the next five features will
otherwise be written, and the offenders are the reason they will be written badly.

### F1.2 — RF-11: the OpenAPI document

`scripts/openapi.mjs` emits OpenAPI 3.1 from `CANONICAL_API_ROUTES` plus
`z.toJSONSchema` on the request bodies (Zod 4 has it). **Generated, never
hand-written** — a hand-maintained document disagrees with the tree within a
release, and a document nobody believes is worse than none.

**Gate:** `docs:check` fails on drift between the generated document and the
manifest.

### F1.3 — CAP-1: the command column, and the flip

Two halves, in order:

1. **The column.** Every register row gains a `command` whose value is a root
   script. `scripts/lib/docs-drift.mjs` already refuses a `pnpm …` citation that
   is not one, so the shape half is unblocked by existing code.
2. **The flip.** `pnpm capability:evidence` (already landed) derives each row's
   status by *running* the command it names and reports `unverified` when it
   fails — closing the half the row says had teeth.

**Gate:** a `real` row whose command fails is a red gate. A row with no command
reports `undecided` rather than passing, which is the honest number.

### F1.4 — Q-1, the authz half

A generated authz matrix: one row per method+path from the canonical list, one
test per row asserting what an anonymous caller receives (200, 401, 403, 501). A
route added without a row fails.

**Gate:** the mirror of the coverage ratchet — the matrix only grows, and the
test that names it is generated rather than written.

The other Q-1 clauses (mutation score, property suites, ceiling 10) stay `debt`
with their recorded conditions: their values are estimates until they are
measured.

## F2 — Make it complete

### F2.1 — One execution domain, done properly

`packages/tool-sdk` and the `api` adapter behind
`POST /api/v1/agents/api/:action`. **One, not five.** Five thin adapters is five
`mock` rows; one real one is a `real` row with a contract, a test, and a register
entry.

It acts on what L0 built: a finding becomes a task, a task becomes a proposed
diff, a human merges. **The console never writes to a repository on its own** —
a generated test that starts green is a hollow test, and the failure-first rule
is measurable: propose, run, assert it fails, only then is it a proposal.

**Gate:** the adapter's own contract test, a register row moved to `real` on the
strength of a command that can fail, and `status:10` point 6 evaluated against the
real result rather than the `501`.

*This is the last unlock from a tool that describes quality to a tool that acts
on it, and it is the one that turns the ledger's `mock` rows into a roadmap.*

### F2.2 — Run the axe suite

`e2e/accessibility/routes.spec.ts` already exists: 13 manifest routes × 2 themes
× 4 data states, plus glass-legibility evidence. It needs `DATABASE_URL` and a
Playwright browser. **This is the evidence UI-1's removal condition (a) names**,
and it is the only item in F2 that is a run rather than a build.

### F2.3 — The Pages workflow

A workflow that publishes `site/.vitepress/dist` and runs
`SITE_DOCTOR_BUILT=1 pnpm site:doctor` against the built output. The `pages:
write` grant is the repository owner's decision; the workflow file is this plan's.

### F2.4 — PostgreSQL 18

`16-alpine` → `18-alpine` in compose and CI. Sequenced after RF-5's rehearsal,
which waits on an 18 instance. **Not before**: the rehearsal is what proves the
migration graph survives the jump, and skipping it is how a version bump becomes
an incident.

## F3 — What stays open, and why that is the correct answer

| Row | Why it cannot close from here |
|---|---|
| RF-9, PERF-1, GLASS-1 | Each needs a measurement on the reference hardware — a self-hosted single-node install. `pnpm render:baseline` is the action, and it belongs to whoever owns that machine |
| DEP-3, DEP-4, RUNTIME-1 | Each waits on an upstream peer range or an LTS date |
| RF-5 | A rehearsal run against a real 18 instance; CI has no second database |
| X-3 | Its removal condition is two *events*: `packages/tool-sdk` existing **and** one domain with a real adapter. F2.1 is that event, and this row names it |
| Q-1's mutation and property clauses | Their values are estimates until measured; recording an estimate is the failure the row exists to prevent |
| C-6, D-4 | Deliberate, with owners and conditions already recorded |

**No number gets invented to close any of them.** That is the one rule in this
repository that has never been traded against, and this plan does not start.

## Order, and the one opinion in it

**F0 → F1 → F2.** The loop before the trust, the trust before the doing. A
console that proves itself trustworthy before it acts is the difference between
a tool and a liability, and the ledger's own rule is the reason: a row claiming
`real` without a command is a claim, not a measurement.

If only one wave lands, it is **F0**. It is one query predicate, one screen, one
derived table — and it is the only one that changes what a tester does on Monday.
