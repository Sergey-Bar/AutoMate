## Wave 1 — The one real core defect

> **TDD rule from AGENTS.md, non-negotiable:** write the test, run it with the defect present, watch it fail for the expected reason, then fix. Three times in this programme a suite was green while checking the wrong thing.

### 1.1 The worker writes `runs.phase`/`outcome`/`status` independently

`apps/worker/src/postgres-store.ts:72-93` `terminalState()` is a hand-written table mapping a status to a `{ job, phase, outcome, legacy }` quadruple. `completeJob` (`:302-315`) then writes those as **three independent columns**.

The API's equivalent calls `deriveRunState(phase, outcome)` — one value derived as a unit — and its comment at `drizzle-execution-store.ts:1420-1423` names this exact defect:

> *"The phase and the outcome are decided together — writing them independently is what made `runs_phase_outcome_check` reachable by a client choice."*

That was found and fixed in the API. **The worker has the same three-column write and never got the fix**, and nothing detects the difference because nothing compares the two.

**The concrete failure.** `terminalState`'s fallthrough (`:87-92`) returns `{ job: 'failed', phase: status, outcome: status, … }` for any status outside `completed`/`cancelled`/`failed`. `deriveRunState` cannot produce that pair: a non-terminal phase always carries `outcome: null`, and every terminal phase carries its own implied outcome. So the worker can write a `(phase, outcome)` pair `runs_phase_outcome_check` rejects — an unhandled 500 on the recovery path, for a request that was well-formed.

**Why it survived.** `worker.ts:65` skips claiming when no handler is set and `main.ts:100` passes none, so `completeJob` is reachable only via `worker.ts:176`, inside the handler branch. Latent defect on dormant code is exactly what survives — the ledger already has this pattern, where RF-1 found the same opt-out *correct* after an earlier sweep read it as the largest gap in the repo.

**Fix — extract the derivation, delete the duplicate.**

1. Move `RUN_PHASES`, `TERMINAL_PHASES`, `PHASE_OUTCOME`, `COMPLETE_OUTCOMES`, `isTerminalPhase`, `isRequestablePhase`, `deriveRunState` from `apps/api/src/execution/phase-outcome.ts` into **`packages/orchestration/src/phase-outcome.ts`**, exported from its `index.ts`. The graph permits it: `apps/api` already depends on `@automate/orchestration` (`apps/api/package.json:18`), which depends on `@automate/shared-contracts` and nothing else (`:23`). Every type needed — `RunPhase`, `RunOutcome`, `PERSISTED_RUN_STATUS_VALUES` — is already in `shared-contracts` (`schemas/execution.ts:31,46`, `test-results.ts:52`).
   - **Leave a re-export** at `apps/api/src/execution/phase-outcome.ts` so its existing importers and both test files keep their path. The import path is not the defect; changing ~6 call sites buys nothing.
2. Delete `terminalState()`. Have `completeJob` derive once: fold the status into a phase the way `drizzle-execution-store.ts:1388-1402` does, then `const derived = deriveRunState(phase, claimedOutcome)` and write `derived.phase` / `derived.outcome` / `derived.status`. `terminal.legacy` disappears with the table — `deriveRunState` returns the column-legal `status`, which is what `runs_status_check` permits. Add `"@automate/orchestration": "workspace:*"` to `apps/worker/package.json`; one workspace dep, no cycle.
3. `JobCompletion.status` is `JobResultStatus`, which is not a `RunPhase`. That folding step is the worker's, because only it knows its own vocabulary; the *derivation* is shared.

**Test — fails today.** Drive `deriveRunState` with the worker's full `JobResultStatus` set and assert each returned triple satisfies `runs_phase_outcome_check` read from the migration and `runs_status_check` from `PERSISTED_RUN_STATUS_VALUES`. Include `'requeue'` explicitly — typed out of `JobCompletion` (`types.ts:63`) but present in the handler's vocabulary, and the input that makes the fallthrough produce an invalid pair. Then a `postgres-store` test that `completeJob` on an expired lease cannot produce a CHECK violation.

**Validation:** `pnpm --filter @automate/orchestration test`, `pnpm --filter @automate/worker test`, `pnpm --filter @automate/api test`, `pnpm --filter @automate/integration-tests test`, `pnpm coverage:ratchet`, `pnpm db:check`.

## Correction log

Two claims from earlier drafts were wrong, both caught by reading rather than by a test:

- **"`ExecutionJob.state` is the 9-value contract union and `mapJob:293` casts a 6-value column into it."** It does not. `apps/api/src/execution/types.ts:44` declares its own 6-value `JobState`, identical to `STORED_JOB_STATES`. No mismatch, no defect — and `fromStoredJobState` having zero callers is **correct**, not dead code. The name collision with `shared-contracts`' 9-value `JobStateSchema` is what made it look like one.
- **"`jobs.routes.ts:53-58` duplicates `jobLeaseIsCurrent`."** It does not. The helper has one caller, the artifacts route. The events route checks `leaseOwner !== runner.id` first, a precondition the helper does not express.

A third, from applying the ladder to this plan itself: **C-4's complexity work was cut.** It was in an earlier draft because the row is `open` — which is not the same as being worth doing. `holdsFence`'s `===` and the in-transaction fencing re-check at `drizzle-execution-store.ts:1381-1382` both stay: the latter is defence against a caller that got past the route, and `runner-lifecycle.drizzle.test.ts` asserts it directly.
