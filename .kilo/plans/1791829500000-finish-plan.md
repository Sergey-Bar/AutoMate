## 1. Four readings that change the plan

These were read out of the tree while preparing this plan, and each one makes a piece of
the closing plan cheaper, dearer, or wrong.

### 1.1 `CANONICAL_API_ROUTES` lives inside a test file

`apps/api/src/route-manifest.test.ts:186` — 89 routes, declared as a literal inside the
test that proves the mount against them. **F1.2 and F1.4 both need that list.** F1.2's
generator and F1.4's matrix generator cannot import a test file's local constant, and a
second copy of the list in a script is the second authority this repository has spent
five waves removing.

**Consequence:** the list moves to `apps/api/src/route-manifest.ts` — a real module, the
single authority — and the test imports it. That is step one of *both* waves, which means
**F1.2 and F1.4 are one wave**, not two. The closing plan's F1 → F2 order stands; its
internal two-step ordering does not.

### 1.2 F2.3 is half built, and the half that is missing is small

`docs.yml` already exists: it builds the site, uploads `site/dist`, and deploys with
`pages: write` and `id-token: write` granted at job level. **The permission decision SITE-1
called "the repository owner's, not a design one" has already been made.**

What is missing is exactly one step in the build job — `SITE_DOCTOR_BUILT=1 pnpm
site:doctor` against the built output — which is the other half of SITE-1's removal
condition. This is a fifteen-minute change, not a workflow from nothing.

### 1.3 The plan's gate for F2.1 names the wrong instrument

The closing plan says F2.1's gate is "`status:10` point 6 evaluated against the real
result rather than the `501`". Point 6 is *the product is instrumented end to end*, whose
clause is decided by `pnpm test:runner` (`scripts/lib/status-ten.mjs:616`). The 501 is not
in `status:10` at all — it is in the capability register, where `automation.agents` and
`automation.chat` are two of the fourteen `mock` rows.

**Consequence:** F2.1's evidence is the register and `capability:evidence`, not point 6.
The correct gate is: the adapter's own contract test, a register row moved to `real` on
the strength of a command that can fail, and `pnpm capability:evidence` still green so the
row is measured rather than typed.

### 1.4 `status:10` never executes a gate — which changes what "done" means

`status:10` states in its own header that it *reads committed files and executes no gate*.
Ten of the twelve rows are decided by a run, a URL, or a database, so a row leaves
`not_configured` only when the artefact it names exists **in the tree**: a recorded CI run,
a live site, a generated document.

**Consequence, and it is the most important line in this plan:** the definition of done in
the closing plan — `pnpm verify:local && node scripts/status:10` with zero `fail` — **is
already met and will stay met.** It is not the measure of finishing. Chasing `status:10`
rows is the trap; the programme-specific artefact list is the measure. This plan tracks
the artefacts, and says plainly which rows will move and which cannot.

## 2. The order, and why

```
F1.1  ──▶  F1.2 + F1.4  ──▶  F2.1  ──▶  F2.3  ──▶  F2.2  ──▶  F2.4
 split     manifest →         the one    the doctor  the axe    blocked
 the store OpenAPI + authz    adapter    step        run
```

**F1.1 first, against the closing plan's own instinct to start with F1.2.** The reason is
not the complexity number — it is that F2.1 is the largest wave and it *writes into the
execution store*. A 2,166-line file with six offenders is where the tool-sdk's artifact
lifecycle would otherwise be written, badly, by someone who cannot see the seams. Split
first; then the adapter has somewhere to go.

**F1.2 and F1.4 together**, because of 1.1. The OpenAPI document is the cheaper half and
lands first, which means the authz matrix lands against a manifest that has already proved
it can generate from itself.

**F2.1 before F2.2 and F2.3**, because it is the only one that changes what the product
*does* rather than how it is checked. The check-only waves after it are the proof that the
new thing is measured and accessible.

## 3. Wave by wave

### F1.1 — split the execution store

**What.** `drizzle-execution-store.ts` (2,166 lines; offenders at 67, 42, 19, 19) and
`in-memory-execution-store.ts` (offenders at 73, 71) split along the seams the files
already contain:

| Module | Owns |
|---|---|
| `*-execution-outbox.ts` | event append, batch writes, retention sweep |
| `*-execution-canonical.ts` | runs, tests, results, summaries, the projection reads |
| `*-execution-artifacts.ts` | artifact bytes, compensation, bounded maps |
| `*-execution-leases.ts` | claim, heartbeat, reap, the lease-scope predicate |

The existing file names stay, as thin composers behind the same `ExecutionStore`
interface. **The interface does not change** — that is the property that makes the parity
suite the proof rather than a hope.

**Order of moves, and it is one at a time.** Outbox → artifacts → leases → canonical,
because the first three are the smallest and the last one is two thirds of the file. After
each move: `pnpm --filter @automate/api exec vitest run src/execution/store-parity.test.ts`.

**Gate.** `store-parity.test.ts` (26 decision scenarios + the execution ones) green after
every single move, and `pnpm complexity` at or below 34 offenders — never a raised ceiling,
which is the whole point and the thing the ratchet would otherwise let a split buy.

**Watch for.** `workspace-isolation.test.ts` claims every file under `execution/` that reads
a workspace id, so each new module needs a row in `WORKSPACE_SCOPED_FAMILIES` in the same
commit as the move — a move that passes its tests and forgets that row fails the next one.

### F1.2 + F1.4 — the manifest, the document, the matrix

**Step one, shared (1.1).** Move the 89-route `CANONICAL_API_ROUTES` into
`apps/api/src/route-manifest.ts`; `route-manifest.test.ts` imports it and every current
assertion stays identical. This step alone must leave all four route-related tests green:
the manifest test, `route-manifest.test.ts` on the web side, the state matrix, and the
docs-drift route check.

**F1.2 — `scripts/openapi.mjs`.** OpenAPI 3.1 from the canonical list, with `z.toJSONSchema`
resolving the request bodies the schemas own (Zod 4 has it). Generated, checked in, and
`docs:check` fails on drift — the same staleness gate the four status pages already use, so
it is one more fixture in `scripts/lib/docs-drift.test.mjs` rather than a new verify step.

**F1.4 — the authz matrix.** Generated: one row per method+path from the canonical list,
recording the response class an anonymous caller receives (200 / 401 / 403 / 404 / 5xx).
Committed, and the check regenerates and fails on drift *and* on a canonical route with no
row.

**The decision the closing plan left open — what the matrix asserts.** There is no
authentication in this product: `auth.sessions` is a `mock` row and every caller is
anonymous, so "what an anonymous caller receives" is *everything* a caller receives. The
matrix therefore records the observed posture as a **golden expectation**: a route whose
answer class changes fails, a route that starts answering 500 fails, a new route without a
row fails, and a row that disappears fails — the mirror of the coverage ratchet, where a
canonical route leaving the manifest is a deliberate baseline update rather than an edit.

**Wiring.** Both generators' checks go *inside* `docs:check`, not as new `verify` steps.
`verify` is budgeted at 20 steps and is at 16 today; a gate that grows the budget is a
question, and folding into an existing step is free.

### F2.1 — one execution domain, done properly

**What.** `packages/tool-sdk` and the adapter behind `POST /api/v1/agents/api/:action`.
One domain, `api`, not five — the plan's own reasoning: five thin adapters are five `mock`
rows, one real one is a `real` row with a contract and a test.

**The shape.** The adapter acts on what L0 built, and no further:
a derived finding becomes a task with the test that fails attached; a task becomes a
proposed diff; **a human merges.** The console never writes to a repository on its own,
and the failure-first rule is the gate rather than a policy: a proposal that cannot name a
failing test is not a proposal.

`packages/tool-sdk` owns the envelope — the action contract, the domain registry, the
proposal type — so the API holds the adapter and the domain holds the semantics, which is
the seam `@automate/reporter` already uses for coverage formats.

**Register.** `automation.agents` (or a new `automation.api` row) moves from `mock` to
`real`, with the adapter's own contract test as its command — a command that fails if the
adapter starts returning a fixture, which is the only reason the row is worth moving.

**Gate (see 1.3).** The adapter's contract test green; the register row's command passing
under `pnpm capability:evidence`; and `GET /api/v1/agents` reporting `api` as implemented
while the other four report `not_configured` — honestly, not by relabelling.

### F2.3 — the doctor step

Add to `docs.yml`'s build job, after `Build`:

```yaml
- name: Run the site doctor against the built output
  run: SITE_DOCTOR_BUILT=1 pnpm site:doctor
```

That is the second half of SITE-1's removal condition; the first half (a workflow that
publishes with the grants) already exists. **One thing to check before closing the row:**
the plan's condition names `site/.vitepress/dist` and the tree builds to `site/dist` (the
site has an explicit `outDir`) — the row's removalCondition and the workflow must agree,
or the row closes against a path that is not the artefact.

### F2.2 — run the axe suite

The spec exists and its routes are derived from `routeManifest`, so it covers 20 route files
× 2 themes × 4 data states by construction. **This is the only wave that is a run rather
than a build**, and it cannot run here: it needs `DATABASE_URL` and a Playwright browser, and
`playwright.config.ts` throws without the database on purpose so an in-memory fallback
cannot report success without PostgreSQL ever being involved.

The work is therefore: (a) confirm the workflow runs `pnpm test:e2e` against a real
PostgreSQL service (it is already a `pr-blocking` check — read the workflow, confirm the
service container); (b) record the numbers — zero serious, zero critical, per route, per
theme — rather than asserting them in prose; (c) if a route fails, fix the screen.

**What can be checked here:** the static half already runs (`route-state-matrix.test.ts`
proves every route file renders four states; the manifest proves every path is registered).
That is the half F0's four states made possible, and it is not nothing — it is the part
that would have caught a route with no error state before a browser ever opened.

---

### F2.4 — PostgreSQL 18

**Blocked, and it should stay blocked.** `16-alpine` → `18-alpine` after RF-5's rehearsal,
which waits on an 18 instance. The rehearsal is what proves the migration graph survives the
jump; skipping it is how a version bump becomes an incident, and this repository has the
ledger row that says so.

What this plan does about F2.4: nothing but record it. The row stays `debt`, and the
compose file keeps 16. **A wave that cannot be evidenced by a command does not close**, and
this is the one the closing plan itself chose to name rather than rush.

## 4. How each wave is checked

Every wave carries a gate that runs **here**, on this host, in `verify:local`. Nothing
depends on a browser, a secret, or a database URL.

| Wave | The gate | Runs here |
|---|---|---|
| F1.1 | `store-parity.test.ts` after each move; `pnpm complexity` ≤ 34 | ✅ |
| F1.2 + F1.4 | `docs:check` fails on drift of either artefact; manifest test proves generation | ✅ |
| F2.1 | adapter contract test + `pnpm capability:evidence` green | ✅ |
| F2.3 | `pnpm --filter @automate/docs build && SITE_DOCTOR_BUILT=1 pnpm site:doctor` | ✅ |
| F2.2 | `pnpm test:e2e` (needs `DATABASE_URL` + browser) | ❌ CI only |
| F2.4 | `pnpm migrate:rehearse` against an 18 instance | ❌ blocked |

## 5. What cannot be checked here, said plainly

- **The axe sweep (F2.2).** `DATABASE_URL` and a browser. The numbers must be recorded from
  a CI run, not asserted from a dev machine.
- **The realtime/e2e durable path.** Same reason — `test:e2e` throws without PostgreSQL on
  purpose.
- **RF-5 and PostgreSQL 18 (F2.4).** A second database and an 18 instance.
- **semgrep and gitleaks.** `security:static` reports `not_configured` under the documented
  `AUTOMATE_HOST_SCANNERS=unavailable` opt-in; CI installs the scanners.
- **The render baseline.** Reference hardware is a self-hosted single-node install; a GitHub
  runner is not it, which is why that job is `pr-reporting` by design.

None of these is closable by writing more code, and the plan does not pretend otherwise.

## 7. Order, and the one opinion in it

**F1.1 → F1.2+F1.4 → F2.1 → F2.3 → F2.2 → F2.4**, for the reason F1.1 carries: split before
the largest feature is written into the biggest file, and generate the manifest before
anything else claims to read it.

**And the opinion, which is the honest part:** of the twelve `status:10` rows, this plan will
move at most one — point 5, when the authz matrix is generated — because ten of them are
decided by runs, URLs and databases that `status:10` itself never executes. **A repository
that finished all of this would still read 1 pass · 11 not_configured**, and that is the
correct reading rather than a failure: the table measures what the tree can prove about
itself, and a run that has not happened is not a fail.

The measure of finishing is the artefact list above, not the table.
