## 3. Track structure and the interlock rule

- **Track Q (quality spine)** — Q0 → Q5. Q0/Q1 land before any product wave merges. Q2–Q5 run continuously.
- **Track P (product capability)** — P0 → P5. Each wave is a gate: a clean checkout must reproduce it.
- **Interlock:** a P-wave may not merge with a red Q gate. Each completed P-wave raises the Q floor for the next (ratchet numbers only go up).
- **Wave size:** keep every PR inside the review budget in Q2 (≤400 changed lines; ≤800 requires a written justification in the PR body). Large refactors are split into mechanical steps so the reviewer stays useful.

**Q0.11 — Contract-safety wave** (§11.2, findings 19–44):

**Item 1 DONE (DB CHECK → classified 4xx).** `apps/api/src/errors/` is now the single error taxonomy. `domain-error.ts` has a `DomainError` with a stable `code` from one `ErrorCode` union and a code→status table, plus `logDetail` for the parts that must never reach a caller; a caller may raise a status into 5xx but not lower a 4xx into a 500, so a client error cannot become an operational alert. `db-errors.ts` maps SQLSTATE to a code **by class**, not by constraint name, so it stays correct as constraints are added: `23514` → `CHECK_CONSTRAINT_VIOLATED` 422, `23505` → `DUPLICATE` 409, `23503` → `VALIDATION_FAILED` 422, `23502` → `MISSING_REQUIRED_FIELD` 400, `22P02` → `INVALID_REQUEST` 400, `40001`/`40P01` → `SERIALIZATION_FAILED` 409 telling the caller to retry, classes 08/53/57 → `DEPENDENCY_UNAVAILABLE` 503, and anything unrecognised → `INTERNAL` 500 with the original kept as `cause`. `boundary.ts` is one `app.onError`/`app.notFound` for the whole app, wired in `index.ts`. `withClassifiedErrors` wraps the execution store and run repository at the composition root so no store method can leak a raw driver error — wrapping method by method is what misses the ones nobody remembers, and it also gives the worker's lease reaper a typed error, which is not an HTTP caller.

  **A real bug surfaced while building this:** Drizzle does not rethrow the `pg` error — it throws its own `Error` whose `cause` carries the code. A classifier reading only the top level classified *every* Drizzle error as `INTERNAL`, which is the bare-500 behaviour the wave exists to remove, and it failed silently because `INTERNAL` is a valid answer. `findSqlState` now walks the `cause` chain, bounded and cycle-safe. A second leak: the constraint name was in `error.message`, which the boundary returns for 4xx, so it reached the client. It now lives in `logDetail` — the log names the constraint, the response does not.

  **Evidence:** `apps/api/src/errors/errors.test.ts` (29 tests) covers the code→status table, every SQLSTATE class, the cause-chain walk, the cycle guard, and that no response contains a stack, a URL or a constraint name. `apps/api/src/errors/db-error-classification.test.ts` proves the chain end to end against the **real migration graph on PGlite**: a `quarantine` row with `ttf_ms` and no `resolved_at` returns **422 `CHECK_CONSTRAINT_VIOLATED`** where it returned an unclassified 500, a missing required column returns 400, and the same row with a resolution returns 201.

  **Still open in this wave:** items 2–8, and the consolidation of the ~20 hand-rolled `error(c, status, code, message)` call sites in the route modules onto `DomainError` — those routes already classify correctly, so that is consolidation rather than a fix.

**Item 2 DONE (safeParse + RUN_SERIALIZATION_FAILED).** `toCanonicalRun` and `canonicalArtifact` called `.parse()`, so a row disagreeing with the canonical schema threw a `ZodError` with no code and no status — which the boundary renders as an indistinguishable 500, identical to a genuine defect. Both now go through `parseOrClassify`, which uses `safeParse` and raises `RUN_SERIALIZATION_FAILED` (a 500, because our projection disagrees with our own contract, but a distinct code so it can be alerted on separately). The Zod issue *paths* go in `logDetail` — enough to name the field in the log, and never in the response.

**Item 9 DONE (phase/outcome derived together; a zero-evidence run is not green).** `runs_phase_outcome_check` makes a run terminal exactly when its outcome is not null, and both stores wrote the two columns **independently, taking the outcome from the event payload** — which is client-controlled. Two consequences: a payload pairing a non-terminal phase with an outcome rolled the whole transaction back and surfaced as an unhandled 500 for a merely malformed request, and a payload could claim `passed` on a run that had run nothing. `apps/api/src/execution/phase-outcome.ts` derives `phase`, `outcome` and `status` as one value: a non-terminal phase always has a null outcome and drops whatever the payload claimed; a terminal phase other than `complete` implies its own outcome, so a cancelled run cannot be reclassified as passed; only a `complete` run may name an outcome, and only from the declared vocabulary. The module also collapses what were **three** phase lists (the event handler's, the in-memory store's, and the new one) into one `RUN_PHASES`, because three disagreeing lists is how a second vocabulary starts.

  A second finding in the same item: `defaultStatus(phase)` in the in-memory store was `if (phase === 'complete') return 'passed'`, so **any** completed phase was reported green, including one where no test ran. A run with no tests, a zero total and no recorded pass now resolves to `interrupted` — the existing "finished without a determinate outcome" value, which keeps the status vocabulary at four members and needs no migration.

  **Evidence:** `phase-outcome.test.ts` (13 tests) proves the CHECK is unreachable from both directions — every non-terminal phase yields a null outcome for every payload shape, and every terminal phase yields a non-null one. `phase-outcome.integration.test.ts` (4) and `phase-outcome.drizzle.test.ts` (5) run the same scenarios through the in-memory store and the Drizzle store on the **real migration graph**, so the constraint is enforced by Postgres rather than assumed. The zero-evidence test is proven fail-before: reverting `statusForTerminal` to return `'passed'` makes it fail.

1. Mirror every DB CHECK constraint in application code (phase↔outcome, counters ≥ 0) so a violation is a classified 409/422, never a 500. — **DONE** (see above).
3. Make the realtime path lossless: isolate each subscriber, advance the SSE cursor only after the listener resolves, log every failure, and make `bus.publish` non-rejecting by contract.
4. Make counter updates transactional, clamped and idempotent: one transaction per event, `FOR UPDATE` re-read, event dedupe key, `greatest(0, …)`.
5. Fix the summary/attempt/retry-count derivations so a run without a summary still produces a coherent, honest `total`.
6. Stop writing in a GET handler; add a unique default-policy constraint; map `23505` to typed conflicts; compensate or defer artifact writes.
7. Fix the dashboard stores: real `name` column, transition guards, audit rows, Zod bodies everywhere, no null-body destructuring.
8. **DONE** — `completionHashes` and `memoryBytes` are gone. `BoundedMap` (insertion-ordered eviction, so a frequently-written key is not the one dropped) and `BoundedByteMap` (bounded by **total bytes**, because one large artifact should evict sooner than a thousand small ones, and an artifact larger than the whole budget is declined rather than pinned) replace them at 10 000 entries and 256 MiB. 9. **DONE** — a run claiming `passed` while executing nothing evaluates to `failed` with reason `evidence:NO_TESTS`. Every threshold sat behind `if (summary.total > 0)`, so such a run evaluated nothing and could gate `ready`. The check is two-sided on purpose — a zero total *and* an empty test array — because a reporter may legitimately omit the summary and still send the tests. And `GateEvaluation.id` now includes the policy hash: `saveGate` upserts on `[runId, releaseId, policyId, policyVersion, policyHash]`, so an id without the hash was a *different* primary key for the same row and the first policy update raised a unique violation instead of updating. **Q0.15 — Contract-authority collapse** (§12.1). The product's central claim is "one contract authority", and the review found six parallel vocabularies that disagree. Collapse them, and add a lint/test rule that fails when a second declaration of a canonical enum appears:

1. **Job state — DONE, as an explicit mapping rather than a merge.** The contract describes a nine-state product machine; the column stores six; only four names overlap, and the machine transitions to `running`, `succeeded`, `waiting_approval` and `expired`, none of which `execution_jobs_state_check` permits. Merging the two would either lose meaning or force a migration for distinctions the store never needs. So `packages/orchestration/src/job-state.ts` declares the mapping explicitly, with each lossy case a stated decision: `running`/`waiting_approval`/`cancelling` → `leased` (the column has no separate states, and `completed_at` distinguishes them), `succeeded` → `completed`, `expired` → `failed`. `job-state.test.ts` reads the real `CHECK` out of the migration and proves every state the mapping can produce satisfies it — a test comparing the mapping against its own list would pass while the database rejected every value. 1. Threat model and security hardening: SSRF/target allowlists, path traversal, CSP and security headers, rate limits, least-privilege service accounts, dependency and image scanning, redaction tests.
2. Storage parity and lifecycle: S3/MinIO completion, retention and legal hold, signed downloads, cleanup, reconciliation.
3. Observability: structured logs, metrics, traces, health/readiness, queue and runner dashboards, alerts — never logging prompts, tokens, raw credentials, or unbounded artifact bodies.
4. Backup, restore, and upgrade: native Postgres and object-store backup, restore rehearsal, migration checkpoints, checksum reconciliation, documented rollback. `migrate:apply` stays blocked until resumable waves and restore evidence exist.
5. Budgets enforced: API latency, dashboard load, run start, event freshness, artifact transfer, queue behavior — measured, with regressions failing CI.
6. Accessibility pass on every visible route, including empty/error/loading states and responsive layouts.
7. Release: digest-pinned images, SBOM, signature/manifest verification, upgrade and rollback scripts, generated changelog.
8. Final truth rewrite: capability register, README, deployment guide, API/CLI reference, recovery runbook, and the product naming.

**Gate:** a new operator installs from a clean checkout, configures secrets, starts the full stack, runs all five domains, inspects evidence, recovers from runner/API/storage failure, restores a backup, upgrades, rolls back, and passes every validation command with no mock on a product path.

## 8. Risks

| Risk | Response |
|---|---|
| The quality gate blocks all product progress | Phase the floors: baseline = today's real numbers, ratchet upward per gate; the gate applies to changed code, not to the 27k existing lines |
| Enforcing `exactOptionalPropertyTypes` + `noUncheckedIndexedAccess` cascades | One package per PR, mechanical, no behavior change, review-cheap; a `// @ts-expect-error`-free conversion is itself a quality win |
| Enabling type-aware lint surfaces hundreds of findings | Triage once into `debt-baseline.json` with owners; fix in the same PR that touches the file; never blanket-disable a rule |
| AI waves need a provider that is not available | Contract tests over injected transport are the gate; live smoke is explicitly `not_configured` (D7) |
| OCI images cannot be built in some environments | `unbuilt` is a PR warning, a release blocker; readiness reports the missing runtime instead of degrading |
| Generated tests could inject code | Generated artifacts are untrusted drafts: parse/validate, approve, then execute only inside an isolated runner |
| k6 AGPL obligations | Keep k6 as an external pinned image; the license check produces the deny-list and the decision is recorded in the SLA doc |
| Scope explosion (this plan is very large) | Waves are independently shippable and independently valuable; each has its own gate and can stop after any wave without leaving a broken product |
| The docs/PRD conflict (FastAPI, InfluxDB, Grafana, Allure, Gemini, KAIROS naming) | The repo plus this plan are authoritative: Hono, Postgres-only durable queue, native reporting instead of Allure/Grafana/InfluxDB, Ollama/Kilo, "Automate" naming. ## 10. Definition of done

1. All five domains execute for real with fixtures, cancellation, timeout, recovery, native evidence, and an explicit blocked state.
